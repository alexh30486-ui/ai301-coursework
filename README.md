## Goal

I wanted a repeatable way to decide whether an issue was a reasonable first contribution. A short description or a `good first issue` label was a starting point, but I also needed to check the repository, the expected work, existing claims, and contribution rules.

The assignment's focus was **“Evidence sources and thresholds, not adjectives.”** I used that idea to make the rubric more specific and to explain why an issue should be accepted or rejected.

## Rubric design

I used five required checks, plus a preferred check for maintainer responsiveness:

| Check | What I looked for |
| --- | --- |
| Maintainer activity | Recent work by people maintaining the repository |
| Repository in use | Evidence that the project is active and not archived |
| Bounded newcomer scope | A clear deliverable with enough information to begin |
| Available to claim | Assignees, comments, or pull requests indicating that someone already owns the work |
| Contribution policy compatible | Whether the contribution follows the project's rules, including any AI restrictions |
| Maintainer responsiveness — preferred | Evidence of maintainer replies to recent issues |

The main refinement I made was to the newcomer-scope check. I wanted it to reject broad umbrella issues while still accepting a single task that happens to touch multiple files.

For example, updating two files to resolve one configuration mismatch can still be bounded work. Counting files alone would miss that distinction. I revised the check to focus on one identifiable deliverable and added explicit failure conditions for work that was too broad.

### Evidence from the successful run

At the time of the live run, the skill reported that:

- The repository was not archived, and its last push was September 16, 2026.
- The five most recent commits were by collaborator `Aburke225` within the previous 30 days.
- All three candidates were unassigned and had no comments or linked or referenced pull requests. No pull requests were open in the repository.
- The contribution guide and pull request template contained no AI restrictions.
- Maintainer responsiveness was unclear: the eight sampled recent issues had no comments from which to measure response time.

Responsiveness was a preferred check, so the unclear result did not prevent acceptance. I kept that uncertainty in the interpretation of the results rather than treating recent commits as proof that maintainers would reply quickly.

## Why I selected issue #73

I chose **#73** because it gives me a clear first task: investigate the disagreement between the README and `.env.example`, determine the expected API-key configuration, and make the instructions consistent.

The skill ranked #72 higher because it better matched the configured technical profile. I understood that recommendation, but I preferred the smaller documentation/configuration task for my first contribution. Acceptance and ranking answer different questions: #73 passed the required checks even though it ranked third for fit.

There is a trade-off. Issue #72 would give me more experience with password validation and tests, and #69 would involve parser behavior. Issue #73 offers less code work, but it lets me focus on understanding the repository, confirming the intended behavior, and preparing a change with a clear review boundary.

I have selected the issue, but I have not claimed or implemented it as part of Unit 1. Claiming, environment setup, and reproduction belong to Unit 2.

## What I learned

The stalled attempts made it important to distinguish an attempted run from a completed one. I needed the full evaluation record and a live response with the expected verdict output before treating either step as finished.

Refining scope was the most useful part of the rubric work. A small file count does not automatically make an issue manageable, and multiple related files do not automatically make it too broad. I needed to look at the actual deliverable and whether there was enough information to begin.

I also learned to use the skill's recommendation as input to my decision. The ranking helped me compare technical fit, while the evidence helped me explain why #73 was still a reasonable choice for my first contribution.

I worked through stalled attempts, refined the scope check, tested the rubric on selected examples, and completed a full evaluation with **20/20 matching verdicts**.
