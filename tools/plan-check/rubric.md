# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
| --- | --- | --- | --- |
| diagnosis-grounded | Issue behavior and repro-evidence inputs, output, and environment compared with the plan's diagnosis. | Pass when the diagnosis explains the observed behavior without contradicting the supplied evidence. A hypothesis may pass when labeled uncertain and paired with a concrete check before the dependent implementation. Fail when the plan ignores decisive evidence or asserts a cause the evidence contradicts. | required |
| cause-targeted | Repro failure location and controls compared with the proposed intervention and expected behavior. | Pass when the intervention addresses the supported failure mechanism or explicitly tests a plausible mechanism first. Fail when it merely suppresses an error, hard-codes success, or changes the symptom while leaving the demonstrated defect. A justified workaround can pass when it delivers the requested behavior and its limitations are explicit. | required |
| scope-bounded | Issue request and thread constraints compared with the plan's changes, affected areas, exclusions, and deviations. | Pass when the work serves one issue outcome and each proposed change is necessary for that outcome or its regression test. Multiple files alone do not fail. Fail for unrelated cleanup, new features, or a broad rewrite without evidence that it is needed. Exclusions may be clear from the work described; a separate heading is not required. | required |
| executable | Candidate plan's implementation actions, locations, dependencies, and order. | Pass when a stranger can identify where to begin, what behavior to change, and how dependent steps connect. A named function or component can be sufficient without exact line numbers or complete code. Fail when a necessary action is only 'fix it', requires unavailable private material, or depends on an unresolved choice with no investigation or decision step. | required |
| test-decisive | Plan's validation steps and expected results compared with the accepted repro trigger and artifacts. | Pass when a proposed check exercises the affected real code path using the issue's trigger or a justified equivalent, with an observable result distinguishing broken from corrected behavior. Cover relevant normal behavior when the proposed change could break it. Fail for only 'run tests', unrelated tests, or a check that would pass with the demonstrated defect intact. Future tests need a stated expectation, not fabricated completed output. | required |
| uncertainty-honest | Repro evidence, diagnosis, risks, validation claims, and any deviation notes. | Pass when observed facts, hypotheses, and future work are distinguishable; consequential unknowns have a way to resolve them before dependent work. Honest bounded deviations pass when the updated approach and reason are explicit and remain grounded. Fail for unsupported claims of completed tests or certainty that exceeds the evidence. Do not require invented risks or deviations. | required |
| thread-aware | Candidate plan comment and plan compared with maintainer instructions, questions, and decisions in thread highlights or the live issue. | Pass when the comment gives an issue-specific approach and verification intent consistent with the plan and relevant thread decisions, or explains an evidence-based reason to propose a different direction. Fail for an interchangeable claim with no actual plan, piggybacking, or ignoring an explicit unresolved maintainer request that affects the approach. An empty thread requires no invented acknowledgment. In live Path Review, another student's plan does not block this one. | required |
| conventions | Repo-facts stated templates and contribution policies compared with the plan and outgoing comment; live mode also reads actual contributing documents. | Pass when applicable explicit requirements are met, including AI disclosure only when required. Fail for a demonstrated violation or a prohibited contribution. Missing evidence of a required condition is unclear. Silence is not a disclosure requirement; polished prose is not evidence of AI authorship. A human-own-words rule alone does not prove a violation. | required |

## Verdict rule

Return accept only when every required check is pass. Any required fail or unclear yields reject. Preferred checks, if added later, never change the verdict. Grade each check independently and report all of them, even after a failure. Use unclear for genuinely insufficient or inaccessible deciding evidence; use fail for a demonstrated contradiction or omission that the pass condition explicitly rejects. Brief writing, missing headings, and lack of implementation code do not independently fail a plan.
