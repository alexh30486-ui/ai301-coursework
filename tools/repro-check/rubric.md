# Rubric: is this reproduction package ready to post?

A package is a claim comment plus a repro report, read against the issue they belong to. Every check below judges the outcome (does the evidence show what the issue describes?), never the write-up's shape. `required` checks gate the verdict; `preferred` checks never change it.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (the "Environment:" line or equivalent), read against the version/platform the issue body and thread name as the target. | The report names the project version AND the platform it ran on (OS, and any runtime the issue turns on: shell, browser, driver, build profile). Those either match what the issue targets (latest release, main, or the reporter's stated version/platform), or the report explicitly calls out the difference. Fail if no environment record exists, if it omits a component the issue says matters (e.g. the driver on a driver-specific bug, the shell on a shell-specific bug), or if it tests a materially different version without acknowledging that. | required |
| steps-followable | The repro report's steps, read from starting state to trigger against the issue's own trigger (exact command, flag syntax, input, config). | A stranger with only public access could re-run every step from the stated starting state to the trigger: inputs, commands, and config are shown or publicly fetchable, and the trigger used is the same one the issue describes (same flag/operator/syntax/expression), not a variant. Fail if any step depends on private code, unshared config, or files the stranger cannot get; fail if the steps swap, drop, or alter the issue's trigger. | required |
| artifact-shows-issue | The report's artifacts (output excerpts, logs, exit codes, screenshots, produced output) read line by line against the behavior the issue describes (error text, exit code, crash vs. graceful error, wrong value, visible symptom). | An artifact is present, and what it shows is the issue's behavior: same error class or message, same exit/crash mode, same wrong output. Fail if there is no artifact, if the artifact only shows the program running normally, or if it shows an adjacent behavior (a validation error instead of a panic, a compile error instead of a runtime error, garbled output instead of a crash, an old version's different error). For an honest cannot-reproduce, pass if the artifact shows the attempt's actual (non-triggering) output. | required |
| outcome-honest | The report's stated conclusion ("reproduced", "confirmed", "could not reproduce", "expected/actual") set next to its own artifacts and environment record. | The conclusion claims no more than the artifacts show. "Reproduced/confirmed" requires an artifact that passes artifact-shows-issue. A cannot-reproduce passes when it says so plainly, shows what it got, and names what differed from the issue (platform, version, data shape) or what a triggering setup likely needs. Fail on root-cause or "verified" claims with no shown evidence, on "confirmed" over a non-matching artifact, on generalizing beyond what was run (e.g. to platforms not tested), or on expected/actual stated backwards from the artifact. | required |
| claim-specific | The candidate claim comment, read against the issue's title, body, and thread. | The claim names something specific to this issue (the symptom, the component, the trigger, or a thread detail) and states a concrete next step that is an investigation or report the author controls. Fail if the comment is interchangeable with any other issue (+1, "me too", "assign me", "great project"), or if it promises a fix, a delivery date, or a guarantee, or asks the issue to be reserved. | required |
| conventions | The repo-facts block's contribution policy and bug-report template, read against both comments. Course packages are AI-assisted work by definition. | If the policy requires disclosing AI use, at least one of the comments states AI was used and to what extent; otherwise fail. If the policy requires comments in the author's own words, the comments read as specific first-person account rather than boilerplate. If the policy is permissive or absent, pass. Fail also if the comments do the thing the repo forbids (e.g. piggyback "same as above" where the repo asks for independent reports). | required |
| control-run | The report's artifacts. | A control run or comparison is shown (the non-triggering input, the working version, or the expected variant) that isolates the trigger. | preferred |
| template-fields | The repo-facts bug-report template asks, read against the report. | The report supplies the fields the template asks for (version, OS, install method, config, etc.) in some form. | preferred |

## Verdict rule

Accept if and only if every `required` check grades `pass`. Any `required` `fail` or `unclear` rejects: proof that cannot be verified from the package is not ready to post. `preferred` checks never change the verdict; report them for the author's benefit only.

In claim-only live mode, env-recorded, steps-followable, artifact-shows-issue, outcome-honest, control-run and template-fields are `unclear` with evidence `not yet applicable: claim-only draft` and are excluded from the rule; the verdict then rests on claim-specific and conventions alone.
